D2F Global source — version 1.1.10+2025

Android app: Flutter. API: backend/ (Express, Prisma, PostgreSQL).
Admin dashboard: admin-dashboard/ (React/Vite).
Direct printer bridge: android/app/src/main/kotlin/com/example/d2f_application/BrotherPrinterBridge.kt
Windows local printer connector: tools/windows-print-connector/.

Before an Android build, review assets/licenses/Brother-SDK-EULA.txt, then run:
  python3 tool/install_brother_sdk.py --accept-brother-license
  flutter pub get
  flutter test
  flutter build apk --release --split-per-abi
The installer retrieves the unchanged official Brother SDK 4.13.2 and verifies
its pinned checksum. The raw proprietary AAR is intentionally not in GitHub.
For an owner-signed ARM64 build, configure private android/key.properties and
run python3 tool/build_android_release.py with Flutter, Android SDK and Java
available. Signing keys and account credentials are never included here.

Backend: npm ci in backend/, configure a private .env from .env.example,
run npx prisma generate and npx prisma migrate deploy, then npm start.
Use an isolated PostgreSQL database for npm test.
Admin dashboard: npm ci, npm test and npm run build in admin-dashboard/.
Windows connector: install Python 3.9+ and the official Brother Windows driver,
then run tools/windows-print-connector/start.cmd. Enter its local pairing key
in the production D2F dashboard's Print Label panel. Configure the correct 4x6
paper and verify physical output. The connector binds only to 127.0.0.1:18441.

Printing targets Brother QL-1110NWB/QL-1110NWBc. Other Bluetooth brands require
separate integration. Actual printer output and Android Play Protect results
remain unverified without physical test hardware. Local release reports record
118 Flutter, 79 backend, 29 dashboard, 4 connector and 74 live API checks passed.

The repository's existing publishing rules exclude Markdown, design inputs and
build outputs. Guides, source archives and signed APKs remain in the owner's
local workspace/deliverables; this commit publishes source and build inputs.

November 2026 operational refresh

Apply the new Prisma migration before running this API version. Notifications
are committed alongside operational changes by database triggers. The API's
push worker retries failed deliveries independently for each registered device.
Covered: Buy for ME and marketplace orders, quotes, customer messages, payment
proof review, shipment and container tracking events, pickup/delivery driver
assignments, Connect bookings/trips/assignments, Ship for ME, seller/product
reviews, payments and returns. Internal staff notes are excluded from payloads.

Railway remains the API/database host. Set FIREBASE_SERVICE_ACCOUNT_JSON in its
backend service's private Variables to enable FCM delivery. Never put this private
credential into Flutter, Git or Vite variables. Firebase initialization uses the
Admin SDK; no Firebase database or authentication migration is required.

Register the Android and iOS apps in the same Firebase project. Add the native
client configuration with FlutterFire (android/app/google-services.json and the
iOS GoogleService-Info.plist included in the Runner target), or supply the
FIREBASE_API_KEY, FIREBASE_APP_ID, FIREBASE_MESSAGING_SENDER_ID,
FIREBASE_PROJECT_ID and FIREBASE_IOS_BUNDLE_ID Flutter dart defines per platform.
For iOS, enable Push Notifications for the signing identifier and upload the
APNs authentication key to Firebase Cloud Messaging. The Runner push entitlement
uses development for Debug and production for Release/Profile. iOS release
signing and APNs access are required for physical-device verification.

In-app notification history works without Firebase. On a real phone, sign in,
allow notifications, and verify registration in the Notifications screen. Send
an admin quote or shipping update; verify the foreground banner, background
notification, cold-start tap, token refresh, logout and two-device delivery.
Live-device push remains unverified until the real Firebase/APNs configuration
is supplied. Android requires Google Play services for FCM delivery.

Connect stores UTC instants with explicit departure/destination IANA zones.
Trip registration uses departure-city civil time, and booking date preferences
follow that city's calendar. Ambiguous or nonexistent daylight-saving times
are rejected. Admins can edit the schedule and country zones before departure.
Legacy trips retain their stored instant; known city zones are inferred for
display and unknown routes show UTC until an administrator confirms the zone.
The dashboard selector controls general admin timestamps and appointment input;
trip departure times always show the route's zone. USA zones are regional.
